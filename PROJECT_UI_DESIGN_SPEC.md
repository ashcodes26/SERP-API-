# Skillup — UI redesign specification for Figma

**Audit date:** 21 October 2026. **Basis:** current working tree, including existing uncommitted changes. **Scope:** repository inspection only; no runtime, provider, database, native-device, accessibility, or test execution in this audit. Only this document was created. Earlier test counts and screenshots are historical evidence, not fresh verification.

**Reading key:** **Existing** = verified in source; **Gated** = implemented but configuration/operational prerequisites apply; **Partial** = backend support or isolated UI actions without a complete current screen flow; **Proposed** = presentation recommendation, not an implemented capability. Source IDs refer to the evidence register at the end. Historical planning documents do not override current routes or components.

## 1. Product overview

Skillup (also called AIMORA in backend identifiers and older documentation) is a career-readiness prototype for students and placement faculty. It connects saved student evidence to target-role requirements, explainable skill gaps, learning resources, professional-asset preparation, and institution-managed placement support. Readiness is informational, never a placement probability or employment guarantee. [E1–E4]

| User | Existing responsibilities and workflows | Permission boundary |
|---|---|---|
| Student | Upload profile evidence; save a role; analyze alignment; build a roadmap; prepare resume/LinkedIn content; search openings and demand; explicitly share a saved resume revision; track applications and assigned preparation | Own student record and private workspaces. Public signup creates students only. |
| Faculty, represented by backend role `admin` | Review assigned-student metrics, cohorts, evidence and shared revisions; analyze cohort gaps; manage drives and training; import students; export scoped reports | Explicit faculty/student and cohort scopes. This is not an unrestricted institution-wide super-admin. |
| Local operator | Provision faculty credentials and grant existing-student access through repository scripts | No corresponding account-management UI; do not invent one in Figma. |

Core flows:

1. Sign in → student Career Plan → profile/document input → save target role → analyze → inspect gaps → deterministic roadmap; optional separately consented Gemini guidance.
2. Opportunities → retrieve listings → inspect source/requirements → compare with saved evidence → hand off to Career Plan or a job-targeted resume.
3. Resume → original text → target → explicit Google consent → Gemini feedback → replace/reject individual edits → factual review → save revision → TXT/DOCX export.
4. LinkedIn → supply/review profile text or public excerpts → save → deterministic positioning feedback → improvement tasks; optional basic-member connection and grounded explanation.
5. Placement Hub ↔ faculty console: student shares a saved revision, faculty provides feedback; students track external applications, training evidence, and assigned quizzes.

Not supported as product features: official ATS evaluation, hiring predictions, recruiter portal, automated employer submission, LinkedIn publishing/full career-history synchronization, OCR, credential authenticity verification, password-reset UI, or full offline operation. A SWOT model/schema exists; no active SWOT screen/generation workflow was found. [E1, E4, E8–E13]

| Layer | Existing implementation | Design consequence |

| Client | Expo SDK 57, React 19.2, React Native 0.86, TypeScript; Expo Router file routes; static web output plus native targets | Design web and native-compatible interactions; desktop browser behavior is not automatically native behavior. | API transport | Typed `fetch` wrapper; bearer authorization; cancellation/timeouts; structured errors; unauthorized callback; longer timeouts for searches/AI | Preserve retryability, disabled in-flight actions, and explicit timeout states; do not replace a failed request with invented data. |

| LinkedIn | Optional server-side OAuth/OIDC connection for basic member identity, callback and polled status; separate indexed-public-search path | Connection is not a full-profile import or publication permission. Pasted/exported profile content remains a distinct path. |

Evidence: E1–E5, E8–E16. Provider secrets belong only on the server. No secret files, credentials, tokens, account records or environment-variable values were inspected or reproduced.

## 4. Current UI audit

### Screen and route inventory

There are **nine user-facing route files**: `/login`, `/`, `/resume`, `/linkedin`, `/jobs`, `/market`, `/placement`, `/admin`, `/admin-import`. `_layout` supplies the shared shell. Faculty sections and student detail use query parameters, not separate route files. Backend OAuth callbacks are integration endpoints, not extra product screens. [E3, E6, E8–E13]

| Current pattern | Evidence-based issue/opportunity | Proposed redesign treatment |
|---|---|---|
| Two UI systems | Career Plan has local Action/Panel/Metric/styles; other pages use `career-ui`; import/login have their own styles. Heading sizes, panel borders, secondary radii and density vary | Create one token/primitive specification with documented compact, standard and editor variants; preserve behavior. [E5, E6, E13] |
| Long single-column workflows | Resume, LinkedIn, faculty detail and Placement Hub render many sequential cards/actions | Use clear sections and progressive disclosure; desktop panels may sit side by side. Keep all existing actions reachable and reading order intact. [E8, E9, E12, E13] |
| Action prerequisites | Resume already lists reasons Gemini is disabled; Career Plan switches Save target role to Analyze only after saving the unchanged target | Reuse this explicit prerequisite treatment across forms; distinguish selected, saved, working and successful states. [E6, E8] |
| Recently simplified profile input | Journey upload now shows Save details after parsing plus Back to profile; the detected-details/skills review panel and checkbox are absent | Preserve that simplified path. Do not reintroduce the removed review card or the removed homepage “MY CAREER PLAN” eyebrow/“STUDENT WORKSPACE” badge. Separate Document Review is still present and must not be confused with it. [E6, E7] |
| Shell/navigation | Visible Log out, four student areas, local asset/opportunity switches; six faculty sections with a compact menu below 900 | Keep account/logout discoverable and current location explicit; reduce competing tab/button styling without changing URLs. [E3] |
| Persistence mismatch | Career Plan focus reload returns to profile/seeded target; LinkedIn success copy points to a to-do list that is not currently rendered | Flag these as functional gaps. Figma must not imply restored target/roadmap position or a reachable task manager without an approved implementation decision. [E6, E9, E11] |
| Metric ambiguity | Faculty analytics uses “Expected x/5,” known means, assessed means and counts in dense strings; many different percent metrics appear across tools | Label “Role-required level,” “Known proficiency mean (n),” “Assessed mean (n)” and “Unknown/unassessed” explicitly. Keep each metric's denominator, scale and source near it. [E10, E13, E16] |
| Demo behavior | Student demo opens extra read-only records above normal content; faculty demo changes the loaded cohort scope and creates persistent synthetic records | Keep small top-right controls; design open/closed/loading/failure states and a clear fictional-data marker. Do not visually merge previews with actual student data. [E17] |
| Dense accessibility surfaces | Many labels/alerts/roles already exist, but some section headings are plain Text, multiple Choices groups use buttons, modal focus behavior is not comprehensively established | Specify heading hierarchy, keyboard/focus order, modal focus return, announced async states, and selected/disabled semantics. This audit does not certify accessibility. [E3, E5, E10, E14] |
| Platform divergence | Web radar has no native chart; progress PDF/DOC export is web-only; resume download uses native sharing; revision editor differs by platform | Design explicit platform variants rather than promising identical charts/downloads. [E10–E12] |

## 5. Eight primary Figma screens

Eight is sensible for **primary screen families**, not eight static frames. The ninth physical route, `/admin-import`, belongs to the faculty screen family. Faculty's six sections, detail/import steps, and student workflow states require variant frames. Do not remove capabilities to satisfy a frame count. The layouts below are **proposed**; data, actions, routes and guards are **existing** unless marked Partial/Gated.

### S1 — Shared sign-in / student signup

- **Route/users/purpose:** `/login`; unauthenticated students and faculty. Authenticate and route to the permitted destination; signup is a mode on this same route.
- **Content/components:** Skillup wordmark, concise product introduction, username/password form, validation/error region, mode switch. Signup additionally collects student ID, name, email, department; password minimum is 12 characters. Reuse login controls and AuthContext flow. [E3–E5]
- **Actions/navigation/API:** Sign in; Create student account; Back to sign in; submit via A. Server returns role; destination is `/` or `/admin`, or a permitted retained deep link. No public faculty signup or forgot-password destination is implemented.
- **States:** Session-restoration loader; editable idle form; in-flight disabled submission; invalid credentials/input; duplicate identity; rate limit/configuration/network failure; authenticated redirect. Preserve entered non-secret form context on failure; never put credentials in mock screenshots.
- **Responsive:** Existing split introduction/form at 900+, stacked below; card capped at 420. Proposed mobile compacts introduction, keeps labels and primary submit visible with keyboard avoidance. Role is not a selectable permission control.

### S2 — My Career Plan

- **Route/users/purpose:** `/`; student-owned evidence → target → alignment → roadmap. Use in-route variants: Profile, Upload, Alignment, Roadmap; no new dashboard route.
- **Content/components:** Title with compact Demo; profile facts/nullable skill bars; Update profile details; distinct Documents to review; role title and optional requirements; Save target role **then** Analyze; alignment/coverage/confidence, gaps/rationale/warnings; deterministic milestones, optional AI plan and exports. Reuse `JourneyInput`, `DocumentReview`, analytics, `CareerRoadmap`, `AiExplanation`, `StudentDemoHeader`. [E6, E7, E11, E14, E17]
- **Actions/navigation/API:** B/C/D/E/M; PDF/DOCX upload → Save details or Back to profile; edit target invalidates the saved-target signature; Analyze → Build roadmap; Back/Edit controls; Reload saved journey. Job match handoff can enter Alignment directly. Document accept/edit/reject is a separate gated subflow with individual source/current/proposed values.
- **States:** Initial/focus loading; absent evidence; unknown proficiency; unsaved/saved/changed target; analysis with no measurable requirements or no gaps; roadmap empty; provider unavailable; profile conflict/stale review; document expiry/deletion; retry and successful save/analysis. Student demo is separate read-only content.
- **Responsive:** Existing max width 960 with 24 padding. Proposed single column on mobile; desktop can group profile/target and metrics without hiding prerequisites. Optional two-panel document comparison must collapse current → proposed → evidence → actions in that order.
- **Fidelity limit:** Do not show editable milestone progress, a full to-do manager, or automatic saved-target resumption as implemented. Those need a separate functional decision. Progress PDF/DOC is browser-only; AI-plan HTML download is browser-only.

### S3 — Resume Analyzer

- **Route/users/purpose:** `/resume`, optional `?job_id=…`; students prepare a saved application document for a manual or retrieved target.
- **Content/components:** Asset subnavigation and five-stage indicator (Add resume → Choose target → Review feedback → Revise → Export); saved-original selector; target controls; consent/prerequisite explanation; Gemini summary/ratings and evidence; independent before/after suggestions; original disclosure; revision editor; final review/save/export controls. Reuse `CareerAssetHeader`, `Field`, `Check`, `Confirm`, analytics and platform-specific `RevisionEditor`. [E8, E12]
- **Actions/navigation/API:** I plus G for targets. Upload PDF/DOCX/TXT or paste; private-storage consent; select/open/delete saved resume; manual title/description or select listing; separate Google consent → Analyze with Gemini; Replace/Undo/Reject; edit; confirm accuracy → Save revision; Restore original; export saved TXT/DOCX. LinkedIn tab and Placement Hub remain accessible.
- **States:** No resume; parsing/loading; target missing; description below 30 characters; consent missing; provider not requested/unavailable/quota/timeout/blocked/invalid/error; nullable ratings; feedback without valid rewrites; unchanged/applied/rejected edits; unsaved draft; stale version; saved revision; export ready/download failure. Preserve edits when requests fail; show confirmation before switching away from dirty editor text through existing replacement actions.
- **Responsive:** Existing 800 max width. Proposed desktop suggestion/editor panels with a clearly identified preserved original; mobile stacks each comparison and keeps save status adjacent to controls. Web editor resizes within bounds; native uses height/accessible controls. Yellow replacement highlighting is presentation-only, absent from exports.

### S4 — LinkedIn Analyzer

- **Route/users/purpose:** `/linkedin`; students improve presentation of supplied professional-profile content. This screen does not publish to LinkedIn.
- **Content/components:** Asset navigation/progress; URL and public lookup consent; source excerpts; editable profile text/export input; storage/analysis consent and own-background confirmation; target-role choices/optional description; quality rubric, sections, evidence strength, positioning, improvements and wording. Reuse `CareerAssetHeader`, `CandidateEvidence`, `LinkedInInsights`, `ImprovementRow`, `AiExplanation`, form primitives. [E9]
- **Actions/navigation/API:** J, F, M. Retrieve public excerpts → explicitly adopt into editor → review/save; upload export; analyze saved text for a curated target or pasted description; Add task; optional Connect → Continue on LinkedIn → return/poll; clear connection; remove profile data with confirmation; open original sources. No auto-publication action.
- **States:** No saved text; URL-only saved; public found/not found/partial data; changed-unsaved editor versus saved analysis; unconfirmed source; unknown proficiency; no improvements; task-created notice; connection pending/exchanging/connected/failed/expired/unconfigured; optional AI unavailable; deletion success and source-analysis invalidation.
- **Responsive:** Existing 1200 max width. Proposed input first, source review and insights as secondary panels at desktop; stacked on mobile. Keep lookup, own-text confirmation and optional Gemini consent distinct. Expose source limitations in every result variant.
- **Fidelity limit:** Add task persists a task, but destination task-list UI is missing. The Figma prototype should annotate this gap rather than fabricate task-management screens.

### S5 — Job Search & Matching

- **Route/users/purpose:** `/jobs`; students discover external listings and compare observed requirements with their evidence.
- **Content/components:** Opportunity switch, compact Demo, role/location/keywords, career-stage query options, listing counts/results, collected time/cache status, selected listing/source/excerpts, evidence/unknown match, gaps and optional roadmap. Reuse `OpportunitiesHeader`, `StatStrip`, `ScoreRing`, `CareerRoadmap`, `AiExplanation`, form/card primitives. [E8, E10]
- **Actions/navigation/API:** G plus D/E/M. Search; next available page; inspect detail; open original source; compare; build roadmap; Continue in My Career Plan through the existing one-use analysis handoff; Enhance resume via `/resume?job_id=…`; inspect this search sample's observed skills; switch to S6.
- **States:** Before search; in-flight; no results; live/fresh-cache/stale-cache; provider missing/rate-limit/timeout/network failure; missing source/company/description; no dictionary-supported actionable requirements; no matching evidence; unavailable alignment; successful comparison/handoff. Do not enable comparison when only unsupported/simple mention requirements exist.
- **Responsive:** Existing 1200 max width. Proposed desktop result list plus selected-detail panel; mobile results → detail with an explicit return control. Preserve selected context and source verification; there is no internal employer-application submission endpoint here.

### S6 — Skill-Demand Insights

- **Route/users/purpose:** `/market`; students interpret retained job samples, compare role samples, and inspect personal evidence coverage.
- **Content/components:** Opportunity navigation, Demo; sample selection/collection form; More options for dates/reset/fresh collection/web CSV; Demand ranking / Role comparison / My skill evidence modes; jobs/skills/search-page counts; last collection/scope/warnings; ranked skills and evidence drill-down; role bars; coverage/radar; source list. Reuse `DemandRanking`, `InsightViews`, `SkillCoverage`, `MarketRadar`, analytics and headers. [E10]
- **Actions/navigation/API:** H plus G to collect a new sample. Analyze Demand; choose retained role; filter skills locally; expand a ranked skill/source; compare 2–3 roles; inspect personal learning priorities/resources; show source jobs; open original posting; return to Career Plan. Collection dates filter collection time, not job posting time.
- **States:** Loading retained data; empty/no sample; insufficient sample; no recognized/matching skills; fewer than two selected roles; unavailable versus 0%; unknown personal proficiency; fewer than three known skills for radar; source unavailable; collect/retry/export success or error. Different query inputs must not silently relabel a prior result.
- **Responsive:** Existing 1280 max width. Proposed desktop filters plus ranked/detail content; mobile compact filters and expandable rows. Radar is web-only and excludes unknowns; native retains exact-value lists. Demand and proficiency are separate quantities, even when charted on the same scale. CSV is web-only.

### S7 — Student Placement Hub

- **Route/users/purpose:** `/placement`; students manage explicitly shared institution-facing activity.
- **Content/components:** Demo and refresh; saved resume/faculty selection and revision history; distinct sharing and stored-Gemini-feedback permission; submitted/approved/change-requested reviews; assigned drives with eligibility reasons/deadline/link; application stages/history; training/evidence and inline assigned quiz. Reuse `ReviewCard`, `ApplicationCard`, `TrainingCard`, `Choices`, forms and shared header. [E13]
- **Actions/navigation/API:** K plus I for saved resumes and E for quizzes. Share selected **saved revision**, revoke sharing, open Resume Analyzer, open employer site, separately record that an application was made, save status/note, open resource, mark training in progress, submit completion evidence, answer every assigned question → submit. No application is automatically sent to an employer.
- **States:** Parallel-load busy/failure/retry via refresh; no faculty, resumes, reviews, drives, applications or training; sharing consent absent; review submitted/changes requested/approved/revoked; eligible/not eligible/needs review or unavailable; existing application; saved status/version conflict; no completion evidence; quiz incomplete/outdated/error/saved score.
- **Responsive:** Existing 1280 max width. Proposed action-focused sections; desktop may use overview/detail columns, mobile one ordered flow. Keep review snapshot/version and sharing scope next to the submission. Application and training states must retain different labels: application `interview`, training `completed`, roadmap `done` are not interchangeable API enums.

### S8 — Faculty console, including import

- **Routes/users/purpose:** `/admin?section=overview|students|analytics|placement|reviews-training|reports`, student detail via `student` query parameter; import at `/admin-import`; assigned faculty only.
- **Shared content:** Account/logout; section navigation; compact Demo; cohort; draft search/department/batch/section/progress filters; Apply filters; Refresh; current applied scope. Reuse `AppNavigation`, `Choices`, `Details`, `ReviewCard`, `ApplicationCard`, `TrainingCard`, `DriveEditor`, analytics and import mapping controls. [E3, E13, E17]
- **Required variants:** (a) Overview metrics with server definitions and follow-up queue; create empty cohort. (b) Paginated Students list → authorized detail containing profile evidence, assessment history, roadmap, shared resume reviews, training and application histories. (c) Skill Analytics: cohort + stored role → required levels, known/assessed means with counts, unknown/missing assessments → student drill-down. (d) Placement Management: drives plus create/edit eligibility/deadline/link form. (e) Reviews & Training: reviews remain contextual to student detail; assign resource/course/project/assessment to selected cohort or opened student, optionally link existing roadmap resource. (f) Reports: applied-scope CSV, optional selected-role gap context. (g) Import: cohort → CSV/XLSX → map/ignore columns → validate/issues → explicitly skip duplicates or update matching assigned records → completion/revalidate remaining rows.
- **Actions/API:** K/L/N; navigate between sections without broadening scope; preserve the opened student when assigning training. Review approval/change request requires feedback and a currently shared submitted revision. Faculty may record eligibility override only with a reason. Demo creates/reuses its separate synthetic cohort and reloads stats.
- **States:** No authorized cohorts/students; no filter matches; no role; no student shared revision; empty assessment/training/application history; draft versus applied filters; aggregates with null means; scope/ownership denial; validation issues; stale versions; duplicate/partial import; loading/retry; successful cohort/drive/training/review/update/export. Report values must come from returned data/definitions, not design-computed totals.
- **Responsive:** Existing max width 1280; import 880. Navigation becomes a faculty-section menu below 900. Proposed desktop student tables/side detail and multi-column metric grid; narrow layouts become labeled rows/cards, not clipped tables. Keep filters, applied scope and actions visible. Import mapping/row issues need mobile stacking and desktop scroll containment.
- **Fidelity limit:** This family needs multiple Figma frames. Do not compress all seven variants into one dashboard mock or omit import merely because it is the ninth route. No screen for faculty provisioning, scope grants, bulk messaging or document-intelligence administration is supported.

## 6. Design system: existing versus proposed

## 9. Constraints for later Codex implementation

- Preserve existing routes, query handoffs, protected stacks, public contract names and server authorization. Faculty is scoped; hiding UI is not authorization. Do not expose student-private resume/LinkedIn/document-review data through a new faculty dashboard.
- Preserve schema/type mirroring. `schemas.py` is authoritative and client contracts must agree. UI rearrangement must not change backend scoring, skill normalization, assessment rules, role requirements or permission scope.
- Keep unknown proficiency `null`; measured zero is valid. Distinguish missing evidence, missing assessment, unknown requirement, empty sample and failed request. Preserve fractions versus displayed percentages and /5 versus /100 scales; retain server explanations and definitions.
- Keep deterministic alignment, sample demand, LinkedIn text quality and subjective Gemini resume ratings visibly separate. Never relabel any as ATS certification, verified capability, eligibility determination or employment probability.
- Preserve explicit boundaries: private resume storage; request-specific Gemini consent; own-text confirmation; optional stored-feedback sharing; retained document-review consent; conflict replacement confirmation. The simplified Journey Save details action is its own explicit save, not the document-proposal approval workflow.
- Preserve original/revised/draft resume separation, exact-passage Replace/Undo behavior, manual edits, highlights, final factual review, version checks and saved-only export. Reanalysis resets decisions; switching dirty editor context needs the existing confirmation behavior.
- Retained document proposals require ownership, current-state comparison, proposal/item versions, conflict review, idempotency and per-item acceptance. Unknown documents/transcripts cannot become inferred academic results. Document deletion/expiry removes retained review data, not previously approved profile facts/minimal audit.
- Do not turn on gated review/grounded AI features or promise their availability. Retained review/AI tables require explicit migrations; operational retention/consent/backup approvals remain external requirements. Redaction is best effort, not anonymity.
- Keep real source URLs, retrieval/cache/provenance labels and unverified-opening notices. No fake live listings, synthetic employer outcomes disguised as real, automatic LinkedIn publishing, or provider calls on page load disguised as passive rendering.
- Preserve student demo read-only isolation and faculty demo's separate persistent cohort. No credentials/key-entry form belongs in the Figma product flows. No provider key, token, credential or environment value belongs in screenshots or this handoff.
- Preserve file constraints: Journey PDF/DOCX; resume/LinkedIn/document preview text PDF/DOCX/TXT, up to 1 MiB; imports CSV/XLSX within server limits. Unsupported/scanned/oversized/invalid files need explicit failure states. Server does not retain original uploaded document binaries.

- Maintain web/native variants, safe areas/keyboard avoidance, reduced-motion/focus behavior and private no-store API handling. Do not imply direct native printing or radar support where only browser implementations exist.
